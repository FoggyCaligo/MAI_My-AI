# MAI 사고 공간 설계

## 1. 문서의 목적

현재 MAI Core는 다음 두 기능을 구현하고 있다.

1. 관찰된 문장을 재사용 가능한 Unit과 CellElement로 누적한다.
2. 현재 입력과 교차하는 과거 구조를 Side View로 찾아 연상 Unit을 인출한다.

현재 `_think_side_view()`가 반환하는 결과는 완성된 사고라기보다 **기억의 인출과 연상**에 가깝다. 이 문서는 인출된 Unit을 임시 공간에서 전개하여 생각을 만들고, 그 생각을 다시 자연어로 표현하기 위한 다음 단계의 개념 모델을 정의한다.

이 문서의 Thought Space와 Expression View는 아직 구현되지 않은 설계안이다. 기존 기억 저장 규칙과 구분하여 다룬다.

## 2. 세 축의 정의

Unit은 어느 한 축이 아니라 모든 축에서 재사용하는 기본 정체성이다.

```text
X축: 구성 요소가 수평으로 연결되어 하나의 Unit을 정의하는 방향
Y축: 만들어진 Unit이 새로운 depth에 쌓이며 관계와 맥락을 형성하는 방향
Z축: 기억에서 선택한 Unit을 임시로 연결하며 사고를 전개하는 방향
```

### 2.1 X축: 개념 덩어리의 정의

X축은 특정 문장 하나의 절대 좌표축이 아니다. 여러 구성 요소가 수평으로 연결되어 **하나의 개념 덩어리인 Unit을 정의하는 구조적 방향**이다.

과거 관찰에서는 구성 요소의 순서가 X축 위에 나타난다.

```text
[비] -> [가] -> [온다]
```

반복되는 구조가 하나의 Unit으로 형성되면 그 Unit의 구성도 X축 방향을 가진다.

```text
[비] + [가] + [온다] = [비가 온다]
```

현재 구현에서 `cell_elements`는 과거 관찰에서 수평 연결이 나타난 순서를 보존하고, `compositions`는 상위 Unit 안에서 자식 Unit이 놓인 순서를 보존한다.

`position`은 전체 기억 공간의 절대 X좌표가 아니다. 특정 관찰이나 Unit 구성 안에서 한 요소가 차지했던 상대적 위치다. Thought는 이 X축 구조를 수정하거나 새 Unit을 정의하지 않는다.

### 2.2 Y축: depth의 누적

Y축은 X축 구조로 정의된 Unit이 다시 하나의 구성 요소로 사용되면서 새로운 depth에 쌓이는 방향이다. 이 누적을 통해 Unit 간 관계와 맥락을 더 높은 구조에서 해석할 수 있다.

```text
[비] + [가] + [온다]
          ↓
      [비가 온다]
```

현재 구현에서는 `compositions`가 각 depth에서 만들어진 부모 Unit과 자식 Unit의 관계를 보존한다. Unit의 depth는 다음 규칙을 따른다.

```text
new_depth = max(child.depth) + 1
```

따라서 depth는 단어, 의미, 개념 같은 고정 언어 계층이 아니며 일반적인 연관관계 점수도 아니다. Unit이 형성된 구조적 높이다.

### 2.3 Z축: 사고의 연결과 전개

Z축은 Side View가 X/Y 기억 공간에서 선택한 완성된 Unit을 꺼내어 임시로 연결하고 사고를 전개하는 방향이다. Z축에 사용되는 Unit의 X축 구성과 Y축 depth는 그대로 유지된다.

```text
[엄마]
   ↓
[출장]
   ├─ [숙박] -> [집에 없음]
   └─ [당일 복귀] -> [저녁 귀가]
```

위 화살표와 분기는 X축 연결이 아니라 Z축의 사고 연결이다. 여러 기억에서 인출된 Unit을 이어 보고, 분기하고, 비교한 흔적이다.

Z축은 단순한 시간 로그가 아니다. 시간적 순서는 사고 구조를 복원하기 위한 좌표로 존재할 수 있지만, 축의 본질은 **현재 활성화된 기억을 배치하고 전개하는 공간**이다.

Thought가 X축을 수정하지 않는다는 것은 중요한 경계다.

```text
X/Y 공간: 기억과 Unit의 정의
Z 공간  : 정의된 Unit을 사용한 임시 사고
```

## 3. Memory, Recall, Thought

MAI의 기억과 사고는 다음 단계로 구분한다.

```text
Memory
  X축으로 정의되고 Y축 depth에 누적된 Unit 구조가 장기적으로 존재한다.

Recall
  현재 입력을 기준으로 Side View를 수행하여 관련 Unit을 인출한다.

Thought
  인출된 Unit을 Z축에 배치하고,
  기존 Unit 구조를 변경하지 않은 채 연결, 분기, 비교, 제거를 반복한다.
```

Side View는 Thought 자체가 아니다. Side View는 현재 초점과 교차하는 기억을 찾아 Z축에 놓을 후보를 제공하는 탐색 방법이다.

```text
입력 Unit 활성화
  -> Side View
  -> 관련 Unit 인출
  -> Z축에 배치하고 사고 연결 생성
  -> 배치된 Unit에서 새로운 초점 선택
  -> 다시 Side View
  -> 다음 Unit 배치
  -> 반복
```

## 4. 사고 구조 자체가 ThoughtPath다

ThoughtPath의 의미를 별도 객체에 복제하지 않는다.

```text
[엄마] -> [출장] -> [외부] -> [집에 없음]
```

위와 같이 Z축에 실제로 놓인 Unit의 연결과 분기 흔적 자체가 사고 경로다. 별도의 다음 구조를 만들어 같은 의미를 중복 저장하지 않는다.

```text
ThoughtPath(
  source="엄마",
  via=["출장", "외부"],
  target="집에 없음"
)
```

가설 역시 별도의 의미 점수나 문장으로 먼저 만들지 않는다. 동시에 가능한 구조를 분기하여 배치한다.

```text
             [숙박] -> [집에 없음]
           /
[출장] ---<
           \
             [당일 복귀] -> [저녁 귀가]
```

각 가지에서 다시 기억을 탐색하고, 현재 입력이나 기억의 연속 구조와 더 잘 이어지는 가지를 계속 활성화한다. 근거를 찾지 못한 가지는 흐려지거나 현재 작업기억에서 제외된다.

## 5. Unit과 Thought상의 출현

장기기억의 Unit 정체성과 Thought 공간에 나타난 한 번의 출현은 구분해야 한다.

동일한 Unit이 한 사고 안에서 서로 다른 가지와 맥락에 여러 번 나타날 수 있기 때문이다.

```text
[엄마] -> [출장] -> [집에 없음]
[엄마] -> [당일 복귀] -> [집에 있음]
```

두 위치의 `[엄마]`는 동일한 `unit_id`를 참조하지만 Thought 공간에서는 서로 다른 위치를 가진다.

초기 구현에서 필요한 최소 개념은 다음과 같다.

```text
ThoughtElement
- 어느 Thought에 속하는가
- 어떤 Unit을 참조하는가
- 어느 ThoughtElement에서 Z축으로 이어졌는가
- Z축의 어느 사고 위치에 놓였는가
- 현재 활성 상태인가
```

`ThoughtElement`는 새로운 의미 Unit이 아니다. 한 사고 과정에서 기존 Unit이 활성화된 위치를 나타내는 임시 요소다.

## 6. 작업기억과 활성화

Thought 공간 전체와 현재 작업기억은 구분한다.

```text
Thought 공간 전체
  이번 사고에서 지금까지 전개된 연결 흔적

Working Memory
  전체 흔적 중 현재 활성화되어 탐색과 비교에 사용되는 일부
```

작업기억의 크기는 제한한다. 새로운 Unit을 활성화하려면 기존 Unit 일부를 비활성화해야 할 수 있다.

```text
[엄마]       활성
[출장]       활성
[내일]       비활성화
[외부]       활성
[집에 없음] 활성
[저녁]       새로 활성화
```

비활성화된 Unit은 사고 흔적에서 삭제되지 않는다. 현재 작업기억에서만 빠지며, 남아 있는 경로를 통해 다시 활성화될 수 있다.

작업기억의 activation은 기존 장기기억 값과 구분한다.

```text
density
  과거 구조에서 실제로 겹친 CellElement의 개수

opacity
  피드백에 의해 조정되는 장기기억의 지속적 가중치

activation
  한 번의 Thought 안에서만 유지되는 임시 활성 상태 또는 강도
```

## 7. 구조적 depth와 사고 위치

Unit의 depth와 사고의 전개 위치는 서로 다른 좌표다.

```text
unitDepth
  Unit이 자식으로부터 합성된 구조적 높이

thoughtPosition
  현재 사고가 전개되면서 해당 Unit 출현이 놓인 위치
```

depth 0인 Unit이 사고의 먼 위치에서 다시 나타날 수 있고, 높은 depth의 Unit이 입력과 동시에 최초 위치에서 활성화될 수도 있다. 두 값을 하나의 depth로 합치지 않는다.

## 8. 최소 사고 사이클

첫 번째 구현은 다음 순서만 수행하는 메모리 기반 프로토타입으로 제한한다.

```text
1. 입력에서 현재 활성 Unit을 얻는다.
2. Side View로 연상 Unit을 제한된 수만큼 인출한다.
3. 인출된 Unit을 Thought 공간의 현재 Z 위치에 배치한다.
4. 작업기억 안에서 다음 초점 Unit을 선택한다.
5. 초점 Unit 주변의 X/Y 기억 구조를 한 단계 탐색한다.
6. 발견한 Unit을 현재 ThoughtElement에서 Z축으로 연결하거나 분기한다.
7. 작업기억의 용량을 넘으면 일부 Unit을 비활성화한다.
8. 변화가 없거나 탐색 한도에 도달할 때까지 반복한다.
9. 최종적으로 살아남은 구조와 전체 사고 흔적을 반환한다.
```

초기 프로토타입의 원칙은 다음과 같다.

```text
- Thought 공간은 메모리에만 존재한다.
- Thought는 기존 장기기억을 수정하지 않는다.
- 작업기억 용량과 최대 탐색 단계는 제한한다.
- 분기를 허용한다.
- 결과를 먼저 구조와 추적 정보로 관찰할 수 있게 한다.
```

사고 결과를 장기기억으로 승격하는 정책은 별도로 결정한다. 자체 사고를 곧바로 외부 관찰과 같은 사실로 저장하지 않는다.

## 9. Thought에서 자연어로

최종 목표는 Thought 구조 자체를 노출하는 것이 아니라 자연어 응답을 만드는 것이다. 그러나 Z축에서 선택된 Unit을 특정 depth까지 단순히 펼쳐 이어 붙이는 것만으로는 자연스러운 문장을 보장할 수 없다.

현재 depth는 고정 언어 계층이 아니므로 다음 등식은 성립하지 않는다.

```text
depth 0 = 문자
depth 1 = 단어
depth 2 = 의미
```

동일한 Thought도 조사, 어미, 순서, 확실성에 따라 여러 문장으로 표현될 수 있다.

```text
Thought:
[엄마] -> [내일] -> [출장] -> [집에 없음]

가능한 표현:
- 엄마는 내일 출장 때문에 집에 없을 거야.
- 엄마가 내일 출장 간다면 저녁에는 집에 없겠네.
```

따라서 자연어 출력은 별도의 생성 지능이 아니라 **기억 기반 Expression View**로 정의한다.

```text
Thought
  무엇을 말할 것인가

Expression View
  그것을 과거에 관찰한 언어 구조로 어떻게 표현할 것인가
```

## 10. Expression View

Expression View는 최종 Thought 구조와 겹치는 과거 X/Y 언어 구조를 찾는다.

```text
1. 최종 Thought에서 전달할 Unit과 가지를 선택한다.
2. 선택된 구조와 겹치는 과거 문장 경로를 찾는다.
3. 가장 잘 이어지는 표현 골격을 선택한다.
4. 현재 Thought Unit을 골격의 대응 위치에 투영한다.
5. 필요한 composition을 선택적으로 하위 Unit으로 펼친다.
6. 마지막 Unit의 content를 연결하여 문자열을 만든다.
```

예를 들어 Thought가 다음과 같다고 하자.

```text
[엄마] -> [출장] -> [집에 없음]
```

기억에 다음 표현들이 있다면:

```text
아빠가 출장 가서 집에 없다
언니는 여행을 가서 오늘 집에 없다
엄마가 회사에 가서 저녁에 돌아온다
```

MAI는 겹치는 X축 구조를 표현 골격으로 사용하고 현재 Thought의 Unit을 대응 위치에 투영할 수 있다.

```text
엄마가 출장 가서 집에 없다
```

MAI가 관찰하지 않은 표현을 능숙하게 생성할 수 있다고 가정하지 않는다. 자연스러운 출력 능력도 관찰된 언어 구조의 누적과 재사용을 통해 성장해야 한다.

## 11. 전체 처리 흐름

```text
Language Input
  -> Unit 활성화
  -> X/Y 기억 공간의 Side View
  -> Recall
  -> Z축 Thought 공간에 Unit 배치
  -> Z축에서 연결 / 분기 / 비활성화
  -> Side View 반복
  -> 최종 Thought 구조
  -> X/Y 언어 기억의 Expression View
  -> 표현 골격 선택
  -> composition 선택적 전개
  -> Natural Language Response
```

이 흐름에서 생각과 언어 표현은 분리한다.

```text
Thought는 답의 구조를 결정한다.
Expression은 그 구조를 이미 배운 언어로 표현한다.
```

## 12. 구현 전에 결정할 항목

다음 항목은 실제 구현 단계에서 하나씩 정책을 확정해야 한다.

1. 최초 Recall Unit을 몇 개까지 Thought 공간에 배치할 것인가?
2. 어떤 활성 Unit을 다음 Side View의 초점으로 선택할 것인가?
3. Side View 후보 중 어떤 Unit을 새로 배치할 것인가?
4. 작업기억의 최대 활성 Unit 수는 얼마인가?
5. 용량을 넘었을 때 어떤 Unit을 비활성화할 것인가?
6. 분기된 사고 구조를 어떤 기준으로 계속 탐색할 것인가?
7. 어떤 상태를 답을 찾은 것으로 판단할 것인가?
8. Thought를 언제 종료할 것인가?
9. Expression View에서 어떤 과거 문장 골격을 선택할 것인가?
10. 사고 결과를 장기기억으로 승격할 수 있는가? 가능하다면 어떤 확인이 필요한가?

이 결정들은 구조에 의미 점수를 임의로 추가하기보다, 기존 MAI의 밀도, 역사적 연속성, composition, opacity 원칙을 최대한 재사용하는 방향으로 구체화한다.
